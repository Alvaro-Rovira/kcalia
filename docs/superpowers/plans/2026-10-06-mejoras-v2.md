# Kcalia mejoras v2 · plan de implementación

> Ejecución: nativa (el propio agente, tarea a tarea, con TDD) y una revisión final con ojos frescos de todo el diff.
> Seguimiento en `docs/PROGRESO.md`; decisiones en `docs/DECISIONES.md`.

**Objetivo:** multiusuario con aprobación y control de gasto de IA, más las funcionalidades de las fases 1 a 5.

**Arquitectura:** FastAPI + SQLAlchemy 2 sobre SQLite con migraciones por `user_version`; filtro automático por
usuario en la sesión ORM; PWA React con cola offline (`outbox.ts`) para toda escritura.

**Stack:** Python 3.12, FastAPI, SQLAlchemy 2, cryptography (push y cifrado de copias), httpx; React 19, TS,
Vite, Tailwind 4, TanStack Query, Recharts (diferido), zxing-wasm (diferido).

**Spec:** `docs/superpowers/specs/2026-10-06-mejoras-v2-design.md`

## Restricciones globales

- Textos en español, tono actual. Colores, radios, sombras y duraciones solo desde `tokens.css`.
- Macros: color + letra + icono, nunca solo color. `prefers-reduced-motion`, mobile first, safe areas.
- Toda escritura del frontend pasa por `frontend/src/offline/outbox.ts` con id generado en el cliente.
- Normalización: Python y TS con el mismo fichero de casos.
- Toda tabla o campo nuevo entra en exportación JSON/CSV (salvo fotos), borrado de datos y borrado de cuenta.
- Tests con cada funcionalidad; flujos de usuario en `e2e/test_flow.py`. Nada llama a servicios reales.
- Dependencias pesadas solo cargadas de forma diferida; no empeorar Lighthouse.
- Commits en español, Conventional Commits, terminados en `Co-Authored-By: Claude <noreply@anthropic.com>`.
- Tras cada tarea: pytest, Vitest, typecheck, ruff, build. E2E al final de cada fase.

## Review Focus

1. Datos de producción reales al migrar (un usuario, comidas, productos con foto): nada se pierde ni cambia de dueño
   salvo hacia el usuario más antiguo. → prueba de migración sobre base v0 con datos (tarea 0.1).
2. Un usuario con la cola offline de otra cuenta en el mismo móvil (cerrar sesión y entrar con otra): el
   `client_id` de otro usuario no debe devolver ni tocar sus datos. → prueba de aislamiento con `client_id`
   repetido (tarea 5.4).
3. Sesión abierta de un usuario que el admin bloquea: la siguiente petición falla. → prueba en 5.5.
4. Sugerencia con historial vacío, objetivo ya superado o calorías restantes diminutas: nunca supera lo que queda.
   → prueba de propiedades (4.3).
5. Datos antiguos sin fibra ni alcohol, y respuestas de IA sin esos campos: siguen validando. → pruebas en 2.2.

### Tarea 0.1 · Migraciones
**Archivos:** crear `backend/app/migrations.py`, `backend/tests/test_migrations.py`,
`backend/tests/fixtures/schema_v0.sql` (esquema actual volcado de `sqlite_master`); modificar `backend/app/db.py`.
**Produce:** `migrations.run(engine, backup_dir) -> list[int]` (versiones aplicadas), `rebuild_table(conn, table,
fill: dict[str, str])`, `CURRENT_VERSION`. `init_db()` = migrar + `create_all`.
**Pruebas:** base v0 con datos → migrada: recuentos iguales, `user_id` del usuario más antiguo, restricciones
nuevas activas, `user_version` correcto, copia previa creada; base nueva → `create_all` directo con la versión
actual; reejecutar no hace nada.

### Tarea 5.4 · Multiusuario
**Archivos:** `models.py` (TenantMixin, columnas de `users`, `AppSetting`, `AdminAudit`), `tenancy.py` (eventos de
sesión: `scope(db, user_id)`, `unscoped(db)`), `deps.py` (`enforce_access`, `require_approved_user`,
`require_admin`), `security.py` (throttle por IP y usuario con espera creciente, validación), `routers/auth.py`,
`usage.py` (`check_ai_budget(db, user)`, `check_stt_budget(db, user)`), `config.py` (ALLOW_SIGNUP,
MAX_PENDING_ACCOUNTS, AI_USER_DAILY_LIMIT, STT_USER_DAILY_LIMIT, ADMIN_AI_DAILY_LIMIT, precios), todos los routers
y `services.py` (sin `select(...).limit(1)` globales: todo pasa por el filtro), `jobs.py` (por usuario),
`scripts/make-admin.py`; frontend `Auth.tsx` (honeypot, mensaje de solicitud), pantalla `Pending.tsx`, tipos.
**Pruebas:** `test_access.py` (todas las rutas: anónimo, pendiente, bloqueado → 401/403; solo públicas
permitidas), `test_isolation.py` (dos usuarios, cada endpoint de lectura y escritura), límites (usuario, global,
pausa, admin aparte), registro (honeypot, tope de pendientes, sin pistas, ALLOW_SIGNUP=false), login (espera
creciente).

### Tarea 5.5 · Administración
**Archivos:** `routers/admin.py` (`/api/admin/users`, acciones, `/api/admin/overview`, `/api/admin/settings`),
`admin_audit`; frontend `pages/Admin.tsx`, badge en navegación, ruta `/admin` solo si `is_admin`.
**Pruebas:** solo admin (403 al resto), flujo solicitar → pendiente → aprobar → usar, bloqueo inmediato, cerrar
sesiones, límites por usuario aplicados, auditoría de cada acción, el admin no puede bloquearse ni borrarse.
